# اجرای اصلاحات قابلیت اتکا و صحت وضعیت Jobها

## هدف

رفع هفت یافتهٔ بازبینی CBM در مسیرهای Apify، اجرای Job، حریم خصوصی دادهٔ خام، تجمیع وضعیت منابع و مستندات جاری؛ بدون اجرای Actor پولی و بدون گسترش دامنهٔ جمع‌آوری داده.

## تصمیم‌های طراحی

1. **شروع Actor و نتیجهٔ مبهم:** فراخوانی غیر-idempotent شروع Actor از retry عمومی جدا می‌شود. پاسخ‌های قطعی خطای provider به‌صورت شکست عادی ثبت می‌شوند؛ خطاهای انتقالی/timeout یا پاسخ‌هایی که ممکن است پس از پذیرش درخواست رخ دهند، به‌عنوان نتیجهٔ مبهم حفظ شده و Job/attempt را به مسیر `needs_review` می‌فرستند، نه retry کور و نه شکست ظاهراً قطعی. GETهای قابل retry رفتار فعلی خود را حفظ می‌کنند.
2. **انتقال نتیجهٔ Places به worker:** handler وضعیت نتیجهٔ جست‌وجو را صریحاً به worker می‌دهد تا `failed`، `aborted` و `timed_out` به موفقیت پیش‌فرض تبدیل نشوند؛ `partial` نیز به‌عنوان نتیجهٔ مجزا باقی می‌ماند.
3. **لغو حین شروع و نهایی‌سازی:** callback پس از ثبت run ID وضعیت لغو را دوباره می‌خواند و در صورت درخواست، run تازه‌ثبت‌شده را abort می‌کند. در نهایی‌سازی، `cancel_requested` همراه با نتیجهٔ `aborted` به `cancelled` ختم می‌شود؛ خطاهای مستقل از لغو همچنان `failed` خواهند بود.
4. **کمینه‌سازی دادهٔ review:** فیلد/آرایهٔ `reviews` از raw allowlist و mapping Lead حذف می‌شود؛ فقط مقدار aggregate `reviewsCount` در Lead و raw مجاز می‌ماند. فیلدهای دیگر و lineage موجود تغییر نمی‌کنند.
5. **تجمیع چندمنبعی:** وضعیت نهایی `succeeded` فقط وقتی همهٔ منابع موفق باشند؛ `failed` وقتی هیچ منبعی نتیجهٔ قابل استفاده نداشته باشد؛ و `partial` وقتی دست‌کم یک نتیجهٔ قابل استفاده وجود داشته باشد ولی نتیجه ناقص/ترکیبی باشد. موارد بدون منبع یا بدون نتیجهٔ قابل استفاده، موفق تلقی نمی‌شوند.
6. **همگام‌سازی اسناد:** roadmap و راهنمای شناخت پروژه بر اساس schema، تست‌ها، منابع فعال/غیرفعال و قابلیت‌های فعلی به‌روزرسانی می‌شوند؛ بخش‌های تاریخی به‌وضوح تاریخ‌دار/آرشیوی می‌شوند تا با وضعیت جاری اشتباه نشوند.

## اجزا و جریان داده

- `src/apify.py`: تفکیک retryهای امن از `start_actor` و طبقه‌بندی نتایج نامعلوم.
- `src/execution/handlers.py`, `src/execution/service.py`, `src/execution/worker.py` و repositoryهای execution: انتشار وضعیت connector، ثبت نتیجهٔ مبهم، جبران race لغو و نهایی‌سازی سازگار.
- `src/connectors/apify_places.py` و persistence: حذف `reviews` از raw allowlist و بررسی عدم ذخیره‌سازی غیرمستقیم آن.
- `src/orchestration.py`: تجمیع قطعی وضعیت منابع و حفظ partial.
- تست‌های Apify، worker recovery، execution service/handler، privacy/persistence و orchestration به‌صورت regression؛ تمام ارتباطات Apify با mock، بدون token واقعی یا Actor زنده.
- `docs/09-roadmap.md` و `docs/13-agent-project-understanding.md`: رفع اعداد/ادعاهای منسوخ و ابهام میان قابلیت تکمیل‌شده و برنامهٔ آتی.

## سازگاری و خطا

- هیچ API عمومی یا schema migration جدیدی هدف این اصلاحات نیست؛ اگر مدل نتیجه نیاز به افزودن فیلد داخلی داشته باشد، مقدارهای پیش‌فرض فعلی حفظ می‌شوند.
- `needs_review` همان مسیر موجود برای تصمیم انسانی دربارهٔ start نامعلوم است؛ سیستم نباید برای چنین موردی Actor دیگری را خودکار آغاز کند.
- لغو در race ممکن است پس از دریافت شناسهٔ run و قبل از abort، چند لحظه تأخیر داشته باشد؛ retry یا abort تکراری باید بی‌خطر باشد و خطای abort نباید وضعیت Job را به موفقیت تبدیل کند.
- حذف `reviews` فقط ذخیره‌سازی آتی را متوقف می‌کند؛ پاکسازی داده‌های قدیمی از دیتابیس بخشی از این تغییر نیست.

## راستی‌آزمایی

1. تست‌های هدفمند regression برای هر هفت یافته.
2. تست‌های مربوط به Apify و execution با mock و سناریوهای timeout، provider failure، لغو هم‌زمان، abort و restart.
3. اجرای کل suite طبق دستور مستند پروژه؛ ثبت دقیق تعداد تست‌ها و هشدارها.
4. بازبینی `git diff` و `git status` برای اطمینان از عدم تغییر فایل‌های حساس/محلی و حفظ تغییر pre-existing در change history.
